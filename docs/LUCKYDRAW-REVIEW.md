# 럭키드로우 빌더 리뷰 — 타로 플랫폼 이식 준비

> 대상: `c:\Users\OS-LAPTOP\Desktop\luckydrawbuilder` (2026-07-20 기준)
> 목적: ① 현재 구조·화면 리뷰 ② Firebase → Supabase 이식 시 매핑 ③ 슬롯 편집기(실시간 미리보기·생성 후 수정) 요구 ④ 수량 운영 워크플로우·다중 뽑기 출현 제한 설계

## 1. 현재 구조 한눈에

```
luckydrawbuilder/
├─ index.html          ← 빌더 UI (테마 폼 + 미리보기 새창 + 배포 안내문 생성)
├─ server.js           ← 빌더 서버 (Express :4000)
│    사이트 1개 생성 = 템플릿 복사 → config.json 주입 → GitHub 레포 생성
│    → GitHub Pages 배포 → Firebase 계정 생성(custom claims) → _global_sites 수명 등록
├─ updateDeleteDate.js ← 구형 사이트를 삭제 대기열에 수동 등록하는 스크립트
└─ base-template/      ← 사이트 1개의 실제 앱 (Vite + React + Tailwind + zustand)
     ├─ DrawPage       ← 메인. 수량 선택 + DRAW (관리자 로그인 필수)
     ├─ ResultReveal   ← 당첨 결과 (1·2등 스크래치 연출 + 컨페티) → 전체 결과 요약
     ├─ AdminPage      ← 상품 테이블, 결과 표시 방식, 리허설/실운영, 잠금, 마감
     ├─ Shipping*Modal ← 방문자 배송정보 입력 / 관리자 목록·엑셀·전체삭제
     └─ useDrawStore   ← Firestore 트랜잭션으로 추첨·저장 (핵심 로직 전부 클라이언트)
```

**타로 플랫폼과의 근본 차이:** 럭키드로우 빌더는 **사이트 1개 = GitHub 레포 1개 = Firebase claims 1쌍**을 찍어내는 공장이다. 타로 플랫폼은 배포 하나에 슬롯이 슬러그로 얹힌다. 이식하면 빌더 서버(`server.js`)·레포 생성·Pages 배포·수명관리(`_global_sites`)는 **전부 사라지고 슬롯 편집기가 대체**한다. 살아남는 건 base-template 의 화면 3개(드로우·결과·관리자)와 추첨 로직뿐이다.

### 운영 모델 (이식할 때 그대로 유지할 것)

- **DRAW 는 방문자가 아니라 스태프가 누른다.** 부스에 놓인 태블릿(웹앱)에 관리자 로그인을 해두고, 방문자가 보는 앞에서 스태프가 뽑는다. 주소 노출 대비로 비로그인 상태에선 DRAW 자체가 비활성. → 타로(방문자가 직접 조작)와 정반대. 슬롯의 서비스별로 "조작 주체"가 다르다는 걸 SlotLayout 설계에 반영해야 한다.
- **리허설 모드**: 추첨해도 재고 미차감. 전날 시연용. 기본값이 리허설이라 실운영 전환을 잊는 사고 방지 문구가 여러 곳에 있다.
- **설정 잠금 / 행사 마감**: 잠금은 스태프 오입력 방지(UI만 비활성), 마감은 추첨 차단(트랜잭션 안에서도 검사). 마감/다시열기만 즉시 저장, 나머지는 "저장하기"를 눌러야 반영.

## 2. 화면별 리뷰

### 2-1. 빌더 UI (`index.html`)

- 테마 폼(폰트·배경 이미지·박스 색/radius/여백·버튼 색·1,2등 하이라이트 색·관리자 링크 색+투명도) → FormData 로 `POST /api/build`.
- **미리보기 새창**이 알차다: React 없이 순수 JS 로 DrawPage/당첨결과/전체결과 3탭을 재현 (스크래치·컨페티 포함). 다만 실제 앱과 **렌더 코드가 이중 구현**이라 화면을 고치면 미리보기도 따로 고쳐야 한다 — 타로 슬롯 편집기의 "실제 컴포넌트를 그대로 미리보기에 쓰는" 방식이 명백히 우월. 이식 시 이 미리보기 코드는 버린다.
- 배포 완료 후 **주최자용 안내 문구를 자동 생성**해 복사하게 해준다(웹앱 설치법, 리허설→실운영 절차, 기능 설명). 이 운영 매뉴얼 내용은 품질이 좋다 — 이식 후에도 주최자 안내문 자동 생성은 살릴 가치가 있다.
- 테마 항목 매핑: boxBgColor(+alpha)·boxRadius·boxPadding·boxMarginTop·buttonBg/Text·buttonRadius·highBg/Text·adminLinkColor(+alpha)·fontFamily·배경 이미지. → 타로 테마 토큰(primary/accent/radius/배경)과 대부분 겹친다. **luckydraw 고유 토큰은 `high`(1·2등 하이라이트) 하나뿐**이라 슬롯 테마에 accent 성격으로 흡수 가능.

### 2-2. 드로우 화면 (`DrawPage.tsx`)

- 수량 스피너(1~100) + 퀵버튼(1/5/10) + DRAW. 남은 수량 ≤ 50 이면 "N개 남았습니다" 배지.
- 추첨은 `drawWithTransaction(drawCount)` 한 방: Firestore 트랜잭션 안에서 ① 마감 검사 ② `totalRemaining >= drawCount` 검사 ③ **남은 수량만큼 티켓을 풀에 깔고 비복원 추출** ④ 실운영이면 remaining/consumed 갱신. → "남은 수량 = 항상 뽑을 수 있는 수량" 불변식이 이미 성립한다. 확률도 남은 재고 비례라 자연스럽다.
- 문제점:
  - **추첨 로직이 전부 클라이언트에 있다.** Firestore 보안 규칙 파일이 폴더에 없어 검증 불가지만, 규칙이 어떻게 돼 있든 관리자 계정 토큰만 있으면 remaining 을 마음대로 쓸 수 있는 구조. Supabase 이식 시엔 **Postgres 함수(RPC) 하나로 원자화**하는 게 정답 (supabase-js 는 클라이언트 트랜잭션이 없기도 하다).
  - 난수가 `Math.random()` — 행사용으론 충분하나 서버로 옮기면 자연히 서버 난수가 된다.
  - `onSnapshot` 실시간 구독으로 여러 기기 재고가 동기화된다. Supabase Realtime 으로 대체 가능하지만, 스태프 기기 1~2대 규모면 폴링/뽑을 때마다 갱신으로도 충분한지 검토 여지.

### 2-3. 당첨 화면 (`ResultReveal.tsx`)

- 저순위 상품은 0.5초 간격 순차 fade-in 으로 자동 공개, **1·2등(하드코딩)만 스크래치 오버레이**(♥ 펄스 → 탭하면 clip-path 로 긁히는 연출 0.7초) + 컨페티. 연출 감각이 좋고 이식 가치가 높다.
- "전체 결과 보기" → 등수·상품별 그룹 요약. 배송 필요 상품이 섞여 있으면 배송정보 입력 버튼 노출.
- 표시 방식(등수만/상품명만/둘 다)은 관리자 설정을 따른다.
- 개선 여지: **하이라이트 대상 등수(1·2등)가 하드코딩** — 슬롯 설정으로 빼자(`highlightRanks`). 상품 수·구성이 행사마다 다르므로.

### 2-4. 관리자 화면 (`AdminPage.tsx`)

- 상품 테이블: 등수(행 순서 자동) / 상품명 / **전체 수량(입력)** / 소진 수량(읽기) / 남은 수량(읽기) / 삭제 / 배송 필요 체크. 하단에 전체·소진·남은 합계.
- 우측 상단: 배송 정보 보기 / 로그아웃 / 행사 마감·다시열기. 좌하단: 설정 잠금, 상품 추가(최대 100). 고정 하단바에 "변경사항 저장하기".
- 저장 로직(`saveToFirebase`)이 신중하다: 트랜잭션으로 원격을 읽어 **consumed 는 원격 값을 보존**(저장 중에도 다른 기기가 추첨할 수 있으므로) 하고 나머지는 로컬로 덮는다. 단 remaining 은 로컬 값으로 덮으므로 저장 직전에 다른 기기가 뽑으면 되돌아갈 수 있다 — 그래서 "수량 변경 시 모든 기기에서 추첨을 멈추라"는 경고가 상단에 박혀 있다. **사람 절차로 레이스를 막는 구조**라는 뜻. Supabase 이식 시 수량 변경도 RPC 로 옮기면(예: "재고를 N 으로 설정" 대신 "재고에 +N/−N") 이 경고 자체가 필요 없어진다.
- `quantity` 입력을 바꾸면 즉시 `remaining = quantity` 로 세팅된다(`updatePrize`). 즉 **"전체 수량" 칸은 사실상 "남은 수량 설정" 칸**이다. 이름과 실제 동작이 어긋나는 지점이고, §5 수량 워크플로우 재설계의 출발점.

### 2-5. 배송 (`ShippingFormModal` / `ShippingListModal`)

- 입력: 당첨 직후 방문자가 이름·연락처·주소 + 개인정보 동의 체크 → `{siteId}/shippingInfo/data` 에 addDoc.
- 목록(관리자): 테이블 + 요약(건수·상품 수) + **엑셀 다운로드**(xlsx) + 전체 삭제. "배송 완료 후 개인정보 반드시 삭제" 경고 배지.
- 우려:
  - 방문자 쓰기가 가능해야 하므로 규칙상 비인증 create 가 열려 있을 텐데, **read 규칙이 어떤지 폴더만으론 알 수 없다.** 열려 있다면 PII 유출. Supabase 이식 시 RLS 로 `insert: anon 허용 / select·delete: 슬롯 주최자만` 을 명시적으로 건다.
  - 제출 즉시 저장이고 수정·중복 방지가 없다(같은 사람이 여러 번 제출 가능). 행사 현장 특성상 큰 문제는 아니나 인지할 것.
  - 자동 파기 장치가 없고 사람이 지워야 한다. 슬롯 수명(기간 접근 제어)이 이미 있는 타로 플랫폼에선 **슬롯 만료 시 배송정보 자동 삭제**를 붙이기 좋다.

### 2-6. 인증 (`useAuthStore` / `RequireAdmin` / `AdminLoginPage`)

- Firebase custom claims `{ isAdmin, siteId }` 로 사이트별 관리자 격리. `isSuperAdmin` 백도어 클레임도 인정.
- 콘솔에 클레임을 세 군데서 `console.log` — 이식 시 제거.
- 타로 플랫폼은 이미 "주최자 계정 자동 발급 + 슬러그 스코프 권한"이 있으므로 **그대로 대체된다.** claims 의 `siteId` ↔ 슬롯 `slug` 가 1:1 매핑.

### 2-7. 빌더 서버 (`server.js`) — 이식 시 소멸

- 잘 만든 자동화(레포 생성 → Pages 활성화 → claims → 수명 등록)지만 타로 플랫폼에선 전부 불필요.
- **주의: 폴더에 `serviceAccountKey.json`(Firebase 관리자 키), `ghToken.txt`, `.env` 가 평문으로 있다.** 이식이 끝나면 키를 회전/폐기할 것. 또한 생성된 각 사이트 레포에 `.env` 가 커밋되어 푸시된다(Firebase 웹 config 라 공개돼도 설계상 무방하지만, 습관으로는 위험).
- 사이트 수명 관리(`_global_sites` + deleteAt = 마감일+15일 + 삭제 봇)는 타로의 슬롯 기간 접근 제어와 역할이 겹친다. 슬롯 만료 정책으로 통합.

## 3. Supabase 이식 매핑

| 럭키드로우 빌더 | 타로 플랫폼에서 |
|---|---|
| 사이트 1개 = 레포 1개 배포 | 슬롯 1개 = 슬러그 (`/{slug}`) — 빌더 서버 전체 소멸 |
| `config.json` 테마 주입 | 슬롯 테마 (`applyTheme`) — `high` 색만 토큰 추가 검토 |
| Firebase Auth + custom claims | 기존 주최자 계정 + slug 스코프 권한 |
| Firestore `{siteId}/settings/prizes/data` (문서 1개에 배열) | `prizes` 테이블 (slug 스코프, RLS) — 상품 1개 = 행 1개 |
| 클라이언트 Firestore 트랜잭션 추첨 | **Postgres RPC `draw(slug, count, …)`** — 행 잠금으로 원자화, 감사 로그(`draw_logs`) 부수 확보 |
| `{siteId}/shippingInfo/data` | `shipping_entries` 테이블 — insert 는 anon, select/delete 는 주최자만 |
| onSnapshot 실시간 동기화 | Supabase Realtime 또는 추첨 응답에 최신 재고 동봉 |
| `_global_sites` 수명 + 삭제 봇 | 슬롯 기간 접근 제어에 통합, 만료 시 PII 자동 삭제 |
| 빌더 미리보기(이중 구현) | 슬롯 편집기가 실제 컴포넌트로 미리보기 |

**설계 결정 필요 — 슬롯과 서비스의 관계.** 지금 `slot.service` 는 단수다. "타로+럭키드로우를 한 주최자 화면에서 관리"를 만족하는 길은 둘:

1. **슬롯당 다중 서비스** (`slot.services: string[]`): 슬러그 하나(`/{slug}`)에 방문자 진입점이 두 개 생기는 문제(탭? 랜딩?)까지 딸려온다. 방문자 UX 를 다시 설계해야 한다.
2. **서비스별 슬롯 + 주최자 대시보드 통합**: 슬롯은 지금처럼 서비스 하나씩 갖고, 주최자 `/admin` 이 자기 소유 슬롯들을 묶어 보여준다(탭 전환). 방문자 경로·슬롯 격리는 그대로.

럭키드로우는 스태프 조작(부스 태블릿), 타로는 방문자 조작(각자 폰)이라 **방문자 진입점을 억지로 합칠 이유가 없다.** ②안이 슬롯 격리 원칙도 지키고 변경 폭도 작다 — **②안으로 확정** (2026-07-20). 같은 행사면 두 슬롯이 테마를 공유하고 싶을 텐데, 그건 "테마 복사" 기능으로 풀면 된다.

**기존 사이트 정책 (확정):** GitHub Pages 로 운영 중인 기존 럭키드로우 사이트들은 **이전하지 않는다** — 수명 정책(마감일+15일 삭제)대로 자연 종료시키고, 신규 행사부터 새 플랫폼을 쓴다. Firestore → Supabase 데이터 마이그레이션 도구는 만들지 않는다.

## 4. 슬롯 편집기 — 실시간 미리보기와 "생성 후 수정"

기존 빌더의 가장 큰 한계 두 가지가 이식의 직접 동기다:

1. **배포 후 수정 불가.** margin·radius·색·폰트가 `config.json` 으로 빌드 시점에 박제된다 — 고치려면 재배포. 이식 후엔 **테마 전체가 슬롯 데이터**이므로 타로처럼 생성 후 언제든 편집기에서 수정한다 (초안 → 저장하기 → 반영, 타로 슬롯 편집기 규칙 그대로).
2. **미리보기가 이중 구현.** 빌더의 미리보기는 실제 앱을 순수 JS 로 따로 재현한 복제품이라, 화면을 고치면 미리보기도 따로 고쳐야 하고 어긋난다. 이식 후엔 **실제 컴포넌트를 그대로 미리보기에 렌더** — 편집기에서 값을 바꾸면 즉시 반영되는 실시간 미리보기(타로 방식)가 기본이 된다.

### 미리보기 요구

- 드로우 화면 / 당첨 결과(스크래치·컨페티 연출 포함) / 전체 결과, 3개 상태를 토글로 전환하며 확인 (빌더 미리보기의 3탭 아이디어는 좋았다 — 실제 컴포넌트 + 샘플 결과 데이터로 다시 구현).

## 5. 수량 운영 워크플로우 재설계

### 현장의 실제 사용 패턴 (요구 — 확정)

1. 행사 전: **오늘 나갈 수량**을 입력
2. 행사 종료 후: 오늘 안 나간 **잔여 수량 확인**
3. 다음 날: **잔여 + 내일 수량**을 직접 계산해 입력
4. 불변식: **입력한 수량 = 지금 뽑을 수 있는 수량. 이게 항상 지켜져야 한다.**

> "+내일 수량만 입력"하는 증분 방식은 검토했다가 기각 — 현장에선 헷갈리는 사람이 많다. **관리자가 칸에 적는 숫자가 곧 뽑을 수 있는 수량**이어야 한다. 덧셈은 사람이 하는 게 맞다(그게 그들의 멘탈 모델이다).

### 설계: "남은 수량" 직접 입력이 단일 진실

- 관리자 표의 편집 칸은 **"남은 수량"** 하나다. 적은 값이 그대로 `remaining` 이 된다. 지금 구현의 동작("전체 수량"을 바꾸면 remaining 이 그 값이 됨)과 같되, **칸 이름을 실제 동작과 일치**시킨다. '전체 수량' 개념은 표에서 뺀다 (매일 재입력하는 순간 거짓이 되는 이름).
- 추첨 가드는 지금처럼 `remaining` 합계 — 불변식이 구조적으로 성립한다.
- 저장은 RPC `set_remaining(prize, n)` 절대값 세팅으로 원자화. 단, 관리자가 40을 보고 90을 적는 사이에 추첨이 일어나면 그 소진분이 덮이는 레이스는 절대값 입력의 본질상 남는다 → **수량 편집은 마감(또는 잠금) 상태에서 하도록 권장 문구 유지** (지금의 "모든 기기 추첨 중지" 경고와 같은 역할, 어차피 운영 절차상 전날 밤에 하는 작업이다).
- 2단계(잔여 확인)는 **마감 리포트**로 지원: 행사 마감 버튼을 누르면 상품별 `오늘 소진 / 잔여` 스냅샷을 보여준다. 관리자는 이 잔여 숫자에 내일 물량을 더해 3단계 값을 적으면 된다 — 확인은 화면이, 덧셈은 사람이.
- `consumed_today`(오늘 소진) / `consumed_total`(누적 소진)은 읽기 전용 통계로 분리. 추첨 RPC 가 `draw_logs`(언제·몇 개·무엇)를 남기면 마감 리포트·분쟁 확인이 공짜로 따라온다.

관리자 표 컬럼 제안: `등수 | 상품명 | 남은 수량(편집, 크게) | 오늘 소진 | 누적 소진 | 배송 | 삭제`.

## 6. 다중 뽑기 시 상품별 최대 출현 제한

### 요구

수량이 많아 확률이 높은 저순위 상품이, 5~10개 일괄 뽑기에서 우르르 쏟아지는 걸 막고 싶다. 예: 5개 뽑기 → 특정 상품 최대 3개, 10개 뽑기 → 최대 5개.

### 설계 제안: on/off 스위치 + 상품별 "묶음 내 최대 비율" (batch cap)

**이 기능은 선택 사항이다 — 원하는 주최자도, 원하지 않는 주최자도 있다.** 따라서 2단 구조로:

- **마스터 스위치 `batchCapEnabled`** (럭키드로우 설정, 기본 **off**): off 면 지금과 100% 동일하게 동작하고 관련 UI(상품별 비율 칸)도 관리자 표에서 아예 숨긴다. 추첨 RPC 는 스위치를 읽어 분기 — 화면이 아니라 서버가 판단한다.
- 스위치 on 일 때만: 상품별 `batchCapRatio`(상품별 미설정 = 그 상품은 제한 없음)

배치 크기별 표(5→3, 10→5, …)를 다 입력받는 것보다 상품별 **비율 하나**가 단순하다. 상한 = `ceil(drawCount × ratio)`.

**기본값은 0.5 를 권한다 — 요구 예시의 숫자가 정확히 나온다:**

| ratio | 5개 뽑기 | 10개 뽑기 |
|---|---|---|
| **0.5** | `ceil(2.5)` = **최대 3개** | `ceil(5.0)` = **최대 5개** |
| 0.6 | `ceil(3.0)` = 최대 3개 | `ceil(6.0)` = 최대 6개 |

1개 뽑기엔 자연히 영향이 없다 (`ceil(0.5)` = 1). 0 은 제약으로 막는다 — "영영 안 나오는 상품"은 재고 0 으로 표현할 일이지 비율로 표현할 일이 아니고, 실수로 0 을 넣으면 왜 안 나오는지 아무도 못 찾는다.

**추첨 알고리즘** (RPC 안, 지금의 티켓 풀 방식 확장):

```
상한선 cap[i] = min(remaining[i], ceil(drawCount × ratio[i]))
풀에 상품별 티켓을 min(remaining[i], cap[i]) 장만 깐다  … (A)
drawCount 회 비복원 추출:
  뽑힌 상품이 cap 에 도달하면 그 상품의 남은 티켓을 풀에서 제거
  풀이 비었는데 아직 뽑을 횟수가 남았다면 → cap 해제하고 재고 있는 상품으로 채움 … (B)
```

- (A) 처음부터 cap 만큼만 깔면 "cap 도달 시 제거"가 자동으로 일어난다.
- (B) 가 핵심 엣지 케이스: **cap 합계 < drawCount 인 순간이 온다** (행사 말미, 저순위만 잔뜩 남았을 때). 이때 선택지는 ① cap 을 풀고 채운다 ② 뽑기 실패를 낸다 — 현장에서 "10개 뽑기 눌렀는데 에러"는 최악이므로 ①로 하되, 결과에 "제한 초과 분"이 섞였음을 관리자 화면에서만 알 수 있게 로그에 남긴다. §5 의 불변식("입력한 수량만큼 항상 뽑을 수 있다")을 cap 이 깨면 안 된다.

### 운영상 트레이드오프 (주최자에게 안내할 것)

- cap 은 확률을 왜곡한다: 저순위를 누르는 만큼 **고순위(비싼 상품)가 이론 확률보다 빨리 소진된다.** 방문자 체감은 좋아지지만 행사 말미에 저순위만 남는 현상이 심해진다 — 이건 버그가 아니라 이 기능의 본질적 대가다.
- 여러 명이 연달아 5개씩 뽑는 경우 cap 은 "한 번의 묶음" 안에서만 작동한다. 묶음을 나눠 누르면 우회된다(스태프가 조작 주체이므로 현장 통제로 충분하다고 판단).
- 기본값은 **off**. 스위치를 켠 슬롯만 이 트레이드오프를 감수한다 — 켜는 화면 옆에 위 안내를 붙인다.

## 7. 이식 우선순위 제안

> **0단계에서 발견된 걸림돌 — 계정 하나에 슬롯 하나.**

> 한 계정이 슬롯 여럿을 가져야 한다. → `0006_multi_slot_admins.sql` 로 PK 를 `(user_id, slug)` 로 옮겼다.

1. ✅ **DB 스키마 + RPC** — `0006_multi_slot_admins.sql`, `0007_luckydraw.sql` 작성 완료.

   **미적용** — 마이그레이션은 SQL Editor 에서 사람이 돌린다.

1-b. ✅ **겸업 주최자 인증 체인** — 0006 이 열어준 다중 슬롯을 코드가 감당하게 했다.

   ✅ `services.ts` 에 luckydraw 등록(조작 주체가 다르다는 사실을 주석으로 못박음).

   camelCase 매핑도 이 파일 안에만 있다.

   흉내 내면 로컬에선 멀쩡한데 현장에서 이중 당첨이 나므로 `ready()` 가 false 다.

   나왔다: `highlightRanks`(1·2등) · `coverMark`(♥) · `lowStockThreshold`(50) · `drawLabel` · `closedText`.
   **색은 여기 없다** — 테마가 이미 갖고 있고 hex 를 tokens.css 밖에 두지 않는다.
   ⬜ 남은 것: 주최자 admin 화면(3단계) · 편집기의 디자인 항목 노출(4단계).

1-c. ✅ **슬롯 수명** (`0009_slot_lifecycle.sql`) — 요구 추가분.
   기간(검수·진행)은 원래 서비스와 무관해 럭키드로우에도 그대로 적용됐다. 바뀐 건 둘:
   - **유예 접근** — `slot_open`(행사 중인가)과 `slot_visible`(접근 가능한가)을 갈랐다.
     럭키드로우는 진행 마감 **+14일**까지 열린다(배송 명단을 꺼내야 하므로). 타로는 유예 0 이라
     판정이 전과 완전히 같다. **추첨은 유예를 안 받는다** — 유예 중에 뽑히면 행사가 안 끝난 것이다.
   - **자동 삭제** — 진행 마감 **+15일**이 지나면 슬롯을 통째로(주최자 계정·질문·상품·배송명단·
     이미지) 지운다. 대상 판정은 DB 의 `expired_slots()` 하나뿐이고, 실제 삭제는 Edge Function 의
     `purge-expired` 가 기존 `purgeOne` 을 그대로 재사용한다(규칙이 두 벌이면 어긋난 쪽이 산 행사를 지운다).
     **마감일을 비우면 영원히 안 지운다**(원본의 `isProtected` 와 같은 fail-closed).
     유예보다 하루 긴 이유: 접근이 막힌 채 남는 그 하루가 되살릴 마지막 창이다.
   ⚠ **스케줄은 켜지 않았다.** 되돌릴 수 없는 작업이라 `select * from expired_slots();` 로 눈으로
     확인한 뒤 사람이 pg_cron 을 건다 (명령은 0009 §5 주석에).

   같이 고친 것 — **이미지 삭제가 새고 있었다.** 기존 `purgeOne` 은 `list(prefix, {limit:200})` 을
   `slug`·`slug/cards` 두 곳에만 돌렸다. 카드 앞면만 78장이고 재업로드가 쌓이면 200을 넘겨
   **넘긴 만큼 남았고**, 폴더 이름이 손으로 적혀 있어 새 폴더는 조용히 빠졌다. 버킷이 public read 라
   남은 파일은 지운 이벤트의 이미지가 계속 공개돼 있다는 뜻이다. 재귀 + 페이지네이션으로 바꾸고
   삭제 수를 로그에 남긴다(되살릴 수 없는 작업이라 "무엇이 사라졌나" 가 유일한 단서다).
3. ✅ **주최자 admin** — `src/admin/luckydraw/` 3화면 + 라우트·메뉴가 서비스로 갈린다
   (합쳐두면 럭키드로우 슬롯에서 `/admin/questions` 가 빈 화면으로 열려 "고장났나" 로 읽힌다).
   - **상품과 수량** — "남은 수량" 한 칸이 곧 뽑을 수 있는 수량(§5). 오늘/누적 소진은 읽기 전용
     (`draw_logs` 에서 센 값이라 손으로 못 고친다) → 이게 곧 마감 리포트다. 저장은 명시적,
     안 하고 나가면 잡는다.
   - **운영 설정** — 리허설·마감·잠금·결과표시·묶음제한. **누르는 즉시 저장**이다:
     대부분 행사 중에 눌리는 결정이라("지금 마감") 저장을 또 해야 하는 토글은 현장에서
     "왜 마감이 안 돼요" 를 만든다. 실패하면 화면을 서버 상태로 되돌린다.
     묶음제한을 켜는 자리에 **대가**를 같이 적었다(비싼 상품이 더 빨리 소진된다) — §6 의 본질.
   - **배송 정보** — 목록 + CSV(엑셀 라이브러리 대신, BOM 붙여 한글 안 깨지게) + 전체 삭제.
     지우기 전에 "내려받았는지" 묻는다 — 사본이 어디에도 없다(방문자도 자기 것을 못 읽는다).
     +14일 접근 / +15일 자동삭제를 화면에서 미리 알린다.
   - **슬롯 전환**(`SlotSwitcher`) — ②안의 실체. 겸업 주최자만 보이고 슬롯이 하나면 안 그린다.
     `repo.slots.list()` 를 안 쓴다(최고관리자용이라 주최자에겐 RLS 로 안 나온다) — slug 별로 읽는다.
4. ✅ **슬롯 편집기** — 실시간 미리보기 + 럭키드로우 화면 설정.
   - **초안이 저장 없이 비친다** (`src/slot/preview.ts`). 편집기가 iframe 으로 초안을
     postMessage 하고 `SlotProvider` 가 저장본 대신 그린다. **타로도 같이 적용된다** —
     SlotProvider 는 서비스를 모른다. 미리보기를 따로 구현하지 않는 게 핵심(원본 빌더는
     순수 JS 로 재현해서 화면과 어긋났다).
     초안일 땐 첫 페인트 배경색 캐시를 **안 남긴다** — 저장도 안 한 색이 방문자 첫 화면에 뜨면 안 된다.
   - **기기 크기가 서비스를 따른다** — 타로는 폰 세로(390×844), 럭키드로우는
     **아이패드 가로**(1180×820). 부스 태블릿이 가로라 폰 세로로 보여주면 미리보기가 제 일을 못 한다.
     iframe 을 좁히지 않고 기기 크기로 그린 뒤 축소한다(좁히면 앱이 모바일 배치로 그려버린다).
   - 럭키드로우는 화면이 하나뿐이라 **뽑기/당첨/전체결과 토글**. 진짜로 뽑을 순 없으니
     가짜 결과를 쓰되 하이라이트 등수를 반드시 섞는다(커버 색·문자를 못 보고 고르면 안 된다).
   - 코드에 박혀 있던 값에 편집 UI: 긁는 등수·커버 문자·버튼 문구·마감 문구·배지 임계값.

   검증 `scripts/verify-preview.mjs` — **저장 없이 색이 따라오는가**가 전부다. 만들면서
   오진을 두 번 했고 둘 다 스크립트에 주석으로 남겼다: ① `input[type=color]` 을 순서로 집으니
   AI '대표 색'(로컬 상태)이라 초안이 안 바뀌었다 ② `page.frames()` 가 편집기 주소도 슬러그를
   포함해 **메인 프레임을 iframe 으로** 잡았다 — 편집기는 고정 라이트라 색이 안 변해
   멀쩡한 기능을 실패로 봤다.
5. 🔄 **검증** — `scripts/verify-luckydraw.mjs` 가 **실제 DB 에 대고** 18가지를 확인한다
   (슬롯을 만들었다 지운다). 이걸 돌리기 전까지 0007·0009 의 SQL 은 **한 번도 실행된 적이 없었다.**
   결과: 추첨 불변식·리허설 무차감·재고초과/마감 차단·묶음제한 억제·리포트 집계·PII 격리 전부 통과.

   **찾은 취약점 (0010 으로 수정)** — `expired_slots()` 가 anon 에게 `200` 으로 열려 있었다.
   만료 예정 슬롯의 **슬러그·행사명이 그대로 샌다**(anon 키는 브라우저 번들에 있으므로 아무나).
   이 함수엔 안쪽 권한 검사가 없다 — 부르는 게 Edge Function 하나뿐이라는 전제였는데 grant 가
   그 전제를 안 지켰다. 단서는 `draw_prizes` 가 anon 에게 `403` 이 아니라 **`400`**(= 함수가 돌긴 했다)을
   준 것이었다. `revoke ... from public` 만으로는 Supabase 의 default privileges 가 준 **직접 부여분**이
   안 뺏긴다 → public·anon·authenticated 를 모두 명시적으로 revoke.
   verify 에 상태코드 검사(`401/403` 이라야 통과)를 넣어 재발하면 걸리게 했다.

   ✅ **화면 검증** — `scripts/verify-luckydraw-ui.mjs` 가 실제로 뽑아본다(슬롯 + 주최자 계정을
   만들었다 purge 로 지운다). 방문자 셸·로그인 게이트·추첨·스크래치·리허설 무차감까지 통과.

   **찾은 버그 2개 (둘 다 럭키드로우 주최자를 통째로 막았다)**
   - `Login.tsx` 가 로그인 후 `/admin/questions` 로 **하드코딩**돼 있었다 — 타로 전용 가정이다.
     럭키드로우 슬롯엔 그 경로가 없어 catch-all 로 떨어졌다.
   - 그 catch-all 의 `<Navigate to="prizes">` 가 **상대 경로**라, 못 찾은 주소를 첫 화면으로
     되돌리는 대신 경로를 덧붙였다 → `/admin/questions/prizes/prizes/prizes/…` 로 URL 이
     무한히 자라는 리다이렉트 루프. 검증이 느렸던 이유도 이것이었다.
   → 로그인은 `/admin` 으로만 보내고 첫 화면은 index 라우트가 정한다(서비스가 늘어도 안 바뀐다),
     catch-all 은 절대 경로로.

   **검증 자체의 함정도 하나 고쳤다.** 처음엔 빈 테마(`{colors:{}}`)로 슬롯을 만들었더니
   `applyTheme` 이 `withAlpha(colors.primary)` 에서 죽어 화면이 하얗게 떴는데,
   "탭바가 없다 / DRAW 가 없다" 같은 **부정 단언은 그대로 통과**했다 — 빈 화면엔 없는 게 당연하다.
   `화면이 그려졌다` · `자바스크립트 오류가 없다` 를 **앞에** 두어 크래시가 통과로 보이지 않게 했다.
