# 검수 프롬프트 — 클래스·디자인·말투의 공통화

> 붙여넣어 쓰는 프롬프트다. 아래 「프롬프트」 절 전체가 입력이고, 그 위는 왜 이걸 하는지다.

## 왜

한 주최자가 슬롯 하나에 타로를 얹고, 옆 슬롯에 롤링페이퍼를, 그 다음에 포토카드를 얹는다.
방문자에게 그건 **세 개의 서비스가 아니라 하나의 생일카페**다. 화면이 서비스마다 따로 자란
탓에 지금은 버튼 높이·빈 상태 문구·뒤로가기 위치·"손님/방문자" 호칭이 서비스마다 다르다.
같은 주최자의 이벤트인데 다른 회사 제품처럼 보인다.

공통화의 목적은 코드 줄 수 줄이기가 아니라 **동일성의 체감**이다. 근거는 여기 남긴다.

---

## 프롬프트

너는 이 레포(생일카페 이벤트 페이지를 슬롯 단위로 파는 플랫폼)를 검수한다.
먼저 `CLAUDE.md`, `docs/DESIGN.md`, `docs/DESIGN_PROMPT_ADMIN.md`, `src/data/services.ts` 를 읽어라.

### 목표 한 줄

**한 주최자가 여러 서비스를 얹어도, 방문자와 주최자 모두 "같은 이벤트, 같은 도구" 로 느끼게 한다.**
서비스가 달라서 생기는 차이만 남기고, 서비스가 달라서 생긴 게 아닌 차이는 전부 없앤다.

### 검수 축 3개

#### 1. 클래스명 · 디자인 일관성

현황은 이미 확인됐다. 이걸 다시 세지 말고, 여기서 출발해 **판단**을 내려라.

- 클래스 체계가 4갈래로 갈라져 있다
  - `ad-*` — `src/styles/organizer.css` (315개, 새 주최자 디자인)
  - `admin-*` / `owner-*` — `src/styles/admin.css` (older, 79 + 35개)
  - 전역 유틸 — `src/styles/components.css` (`.btn` `.surface` `.tile` `.chip` `.list-row` …)
  - CSS 모듈 35개 — 화면·서비스별
- 모듈 안에서 같은 이름이 계속 재발명된다: `.card`×18 · `.stage`×17 · `.head`×13 ·
  `.backBtn`×10 · `.summary`×8 · `.empty`×8 · `.actions`×8 · `.overlay`×7
- 공통 컴포넌트에 서비스 이름이 박혀 있다: `components.css` 의 `.tarot-card`

물어볼 것:

- 이름이 같은 18개의 `.card` 는 **같은 것인가 다른 것인가.** 같다면 왜 18번 다시 쓰였고,
  다르다면 왜 같은 이름인가. 시각적으로 대조해 판정하라(눈으로 CSS 만 보지 말고 실제로 띄워라).
- `ad-*` 와 `admin-*`/`owner-*` 는 **한 체계로 수렴 중인가, 두 체계가 영구히 공존하는가.**
  수렴 중이면 어디까지 왔고 남은 화면은 무엇인지 목록으로 내라.
- 서비스 모듈이 `components.css` 의 공통 클래스를 **쓰지 않고 같은 스타일을 재선언한** 자리를
  전부 찾아라. `components.css` 머리말이 "여기 있는 스타일을 재선언하지 말 것" 이라고 명시하는데
  지켜지고 있는지가 쟁점이다.
- hex 가 `tokens.css` 밖에 나온 자리, 토큰 대신 하드코딩된 px/radius/그림자.

#### 2. 서비스 무관 공통화

`src/` 아래 서비스 디렉터리 — `luckydraw` `rolling` `photozone` `wish` `poll` `stamp` `quiz`
`photocard` `cheer` `screens`(타로) — 와 각각의 관리 화면(`src/admin/<service>/`)을 **가로로**
비교하라. 세로(서비스 하나를 끝까지)로 읽지 말고, **같은 역할의 화면끼리** 묶어서 읽어라.

가로로 묶이는 것들 (최소한 이만큼은 봐라):

| 반복되는 것 | 어디서 반복되나 |
| --- | --- |
| 화면 셸 (헤더·뒤로가기·타이틀·바닥 CTA) | 모든 서비스 |
| 시작 화면 (안내 → 시작 버튼) | luckydraw · quiz · stamp · photozone |
| 참여 결과 공개 (연출 → 결과 카드 → 저장/공유) | luckydraw · photocard · quiz · photozone · 타로 |
| 목록 + 빈 상태 + 페이지네이션 | rolling · wish · poll · admin 전역 |
| 입력 폼 (라벨·에러·글자수·제출바) | rolling · wish · cheer · luckydraw 배송지 |
| 종료·마감·기간 밖 안내 | 전 서비스 |
| 관리 화면의 통계 타일 · 표 · 내보내기 · 위험한 작업 확인 | `src/admin/*` 전부 |

각 묶음마다 판정하라:

- **공통 컴포넌트로 뽑을 것** — 시각·행동이 이미 같거나, 달라야 할 이유가 없는 것
- **공통 뼈대 + 서비스 슬롯** — 구조는 같고 안에 들어가는 것만 다른 것
- **그대로 둘 것** — 서비스의 정체성이 거기 있는 것 (럭키드로우의 스크래치, 타로의 카드 뒤집기,
  소원나무의 등불). 이건 **공통화 대상이 아니다.** 억지로 묶으면 서비스가 죽는다.

판정마다 근거를 한 줄로 적어라. "비슷하니까" 는 근거가 아니다.

#### 3. 말투 · 어투 · 용어

현황(코드 전체 빈도, 주석 포함):

- 방문자를 부르는 말: **손님 240 · 방문자 194 · 팬 17 · 고객 16 · 사용자 18**
- 운영 주체: **관리자 244 · 주최자 236 · 스태프 129 · 호스트 1**
- 어투가 한 파일 안에서도 섞인다 — `src/admin/QuestionEditor.tsx:150` "…방문자에게 나갑니다."
  vs `src/admin/Dashboard.tsx:235` "…자료가 파기돼요."

할 일:

1. **화면에 나가는 문자열만** 따로 추려라(주석·변수명·타입은 2차). 누가 읽는 화면인지로 갈라라 —
   방문자 화면 / 주최자 화면(`.admin`) / 슬롯 편집기(`.owner`) / 스태프 화면.
2. 독자별로 **호칭·어투를 하나로 확정**하고 표로 내라. 확정 뒤에 어긋난 자리를 전부 목록화하라.
   - 주최자 화면에서 방문자를 뭐라 부르는가 — 손님인가 방문자인가. 하나만 산다.
   - 존댓말 종결 — "~합니다" 인가 "~해요" 인가. 화면 종류에 따라 갈라도 되지만 **규칙이 있어야** 한다.
   - 파괴적 동작(삭제·마감·초기화)의 문구 톤은 나머지와 달라도 된다. 다르다면 그 규칙도 적어라.
3. **서비스마다 다른 이름으로 부르는 같은 개념**을 찾아라. 응모/참여/뽑기/도전, 경품/선물/보상,
   마감/종료/닫기 — 주최자가 두 서비스를 같이 쓸 때 같은 개념이 다른 단어로 나오면 그게 균열이다.
4. 서비스 라벨·힌트(`src/data/services.ts`)와 실제 화면 문구가 어긋나는지 대조하라.

### 건드리면 안 되는 것

- 슬롯 격리(테마·질문·권한이 slug 스코프)를 깨는 공통화
- **조작 주체 차이** — 타로는 방문자가 자기 폰으로, 럭키드로우는 스태프가 부스 태블릿에서.
  화면을 공통화하면서 이 권한 경계를 넘기지 마라 (`docs/LUCKYDRAW-REVIEW.md`).
- 최고관리자/주최자 역할 분리 — 슬롯 편집기를 `/admin` 쪽으로 끌어오지 마라
- 슬롯 이미지의 `<img>` 금지 — 예외는 `SavableImage` 하나. 공통 컴포넌트를 만들면서 `<img>` 를
  새로 들이지 마라 (`npm run verify:noimg` 로 확인)
- `.admin`·`.owner` 의 고정 라이트 — 관리 도구는 어느 슬롯에서 열든 같은 색이다

### 내는 것

`docs/` 아래 마크다운 하나. 순서는 심각한 것부터.

각 항목:

```
### [축] 한 줄 제목
- 무엇이: 사실 (파일:줄 근거 2~3개, 전부 나열하지 말고 대표만)
- 왜 문제: 주최자/방문자가 무엇을 다르게 느끼는가 — "일관성" 같은 추상어 금지
- 어떻게: 구체적 제안 + 영향 범위(파일 수)
- 등급: 지금 / 다음 서비스 얹기 전 / 언젠가
```

마지막에 **규칙 절**을 붙여라. 앞으로 새 서비스를 얹을 때 지킬 클래스 명명·공통 컴포넌트 사용·
용어·어투 규칙을 각 5줄 이내로. 이 절이 이 검수의 진짜 산출물이다 — 이번 정리는 한 번이고
규칙은 계속 쓰인다.

### 지킬 것

- **실제로 띄워서 봐라.** 포트 5174, `npm run shot <경로> <출력>`. CSS 를 읽고 "같아 보인다" 로
  판정하지 마라 — 스크린샷으로 나란히 놓고 판정한다. 최소한 서비스별 시작 화면·결과 화면·
  주최자 대시보드는 캡처해서 비교하라.
- 이 프롬프트에 이미 적힌 현황 수치를 다시 세느라 시간 쓰지 마라. 검증만 하고 넘어가라.
- **이번 턴에 코드를 고치지 마라.** 검수 문서와 규칙만 낸다. 적용은 승인 뒤 따로 한다.
- 전면 리팩터를 제안하지 마라. 서비스가 계속 늘어나는 중이라 한 번에 갈아엎으면 다음 서비스가
  막힌다. **순차 적용 가능한 단위**로 쪼개서 내라.
