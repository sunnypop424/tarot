## 1. ✅ [축1+축2] 주최자가 고른 색·형태가 7개 서비스에 닿지 않는다

- **무엇이:** 데모 슬롯 11개는 **테마가 전부 같다**(`canvas #f7f5ff` / `primary #816bff`).
  그런데 화면은 갈라진다 — 타로·럭키드로우만 보라로 뜨고, 모의고사·투표·스탬프·포카는

  슬롯이 고른 모서리가 3분의 2에 안 닿는다.

  `headText || theme.colors.fg1`. 저장된 값이 있으면 그대로 이기므로 **기존 슬롯은 안 바뀐다.**
  시안의 중립색을 유지해야 하는 자리(포카 덱 무대, 포토존 촬영 화면)는 지금처럼 고정하고

## 4. [축3] 한 화면 안에서 손님·방문자·고객이 같이 나온다

- **무엇이:** 주최자 대시보드 캡처 **한 장**에 셋이 다 있다 —
  상단 배너 "고치면 **고객** 화면에 바로 반영돼요"(`AdminLayout.tsx:252`),
  사이드바 "**방문자** 페이지 열기"(`:196`),
  바로가기 "**손님**에게 보이는 화면을 확인해요"(`Dashboard.tsx:336`),
  통계 캡션 "**방문자**에게 보이는 질문"(`:350`).
  게다가 사이드바 링크와 바로가기 카드는 **같은 주소인데 이름이 다르다**
  ("방문자 페이지 열기" vs "내 페이지 보기"). 방문자 화면은 애초에 2인칭을 안 써서
  이 균열은 **주최자·편집기 화면에서만** 생긴다.
- **왜 문제:** 주최자가 "고객"이 자기를 말하는지 손님을 말하는지 화면마다 다시 읽어야 한다.
  실제로 편집기 점검표(`owner/readiness`)에서는 "**고객**이 관리 화면에 못 들어가요"의 고객이
  주최자고, 바로 아랫줄 "**손님**이 고를 게 없어요"의 손님이 방문자다 — 한 카드 안에서
  두 단어가 서로 다른 사람을 가리킨다.
- **어떻게:** 확정대로 **화면 문구는 "손님", 코드·타입·문서는 "방문자"**. 같은 주소를 여는
  두 링크는 "내 페이지 보기"로 통일한다. 영향: `.admin`·`.owner` 문자열 약 40곳.

  2. 관리·편집기 **40여 개 경로를 실제로 띄워** 모은 DOM 클래스 220개에도 없다

  적용 뒤 같은 수집을 다시 돌려 **지운 선언 중 화면에 뜨는 것이 0개**임을 확인했다.
  `verify-admin` 통과 · `verify-owner` 38/40(2건은 이 변경 전에도 같은 실패) ·
  편집기·주최자 계정 패널·로그인·대시보드 캡처가 이전과 같다.

## 16. ✅ [축1] 관리 도구의 상태색에 이름이 없다 — "위험" 빨강만 다섯 가지

> 8번을 적용하다 발견했다. 원래 조사분에는 없던 항목이다.

- **무엇이:** `admin.css` 의 토큰 블록 **밖**에 hex 27건이 흩어져 있다. 절반은 위 토큰과 같은
  값을 다시 쓴 것이고(`#505050`·`#8a8a8a`·`#816bff`·`#f0edff`), 나머지는 이름 없는 상태색이다.
  같은 뜻의 빨강이 다섯이다 — `#b23b3a`(`:343`) `#f16361`(`:831`) `#e0605e`(`:980`)
  `#c0504e`(`:1341`) `#d4504e`(`:1354`). 성공 `#3ea472`, 경고 `#e0a33a` 도 이름이 없다.
- **왜 문제:** 주최자가 위험한 동작(삭제·마감·초기화)을 만나는 화면마다 경고의 빨강이 미묘하게
  다르다. 같은 위험도인지 아닌지를 색으로 읽을 수 없다. 8번의 hex 예외를 선언해도 **값이 한
  곳에 없으면** 규칙이 다시 무너진다 — 1번과 같은 모양의 문제다.
- **어떻게:** 토큰 블록에 `--ad-danger` / `--ad-danger-wash` / `--ad-ok` / `--ad-warn` 을 만들고
  27건을 그 이름으로 바꾼다. 다섯 빨강 중 무엇을 남길지는 **캡처로 대조해 하나 고른다**
  (파일만 읽고 고르면 어느 화면이 달라지는지 모른다). 영향: `admin.css` 1개 파일.
- **등급: 다음 서비스 얹기 전**
- **적용됨 (2026-07-29) — 15번이 대부분을 대신 해결했다.** 흩어진 hex 27건 중 **24건이 죽은
  규칙 안에** 있어서 규칙째 사라졌다. **다섯 빨강도 색을 고를 필요가 없어졌다** — 다섯 다
  삭제된 자리(`.admin-banner--err`·`.admin-result`·`.stat-*`·`.admin-code` …)에 있었고,
  살아남은 위험색은 토큰 블록의 `--color-error` 하나뿐이다. `--color-error` 주석에 그 경위를
  적어 "새 빨강을 만들지 말고 이걸 쓴다"로 못박았다.

  남은 3건은 이름을 붙였다: `#505050`→`var(--color-fg-2)`, `#8a8a8a`→`var(--color-fg-3)`,
  `#faf9fc`→새 토큰 `--color-row-hover`. 포커스 링의 `rgba(129,107,255,0.18)`(brand 18%)도
  같은 성격이라 `--color-focus-ring` 으로 뺐다.
  **결과: 토큰 블록 밖 색 리터럴 0건**, 머리말이 그렇게 적을 수 있게 됐다.

**클래스 체계 수렴 여부:** 프롬프트의 전제 "두 체계가 공존"은 사실과 다르다. `src/admin/`
28개 tsx 는 사실상 전부 `ad-*` 로 넘어갔고, 남은 `admin-portal` 1건(`AdminFeedback.tsx:69`)은
포털이 `.admin` 서브트리 **밖**으로 나가서 생기는 구조적 예외다. `src/owner/` 가 `ad-*` 를
안 쓰는 건 미완이 아니라 `organizer.css:4-6` 이 명시한 **의도된 영구 분리**다(두 도구가
클래스를 나눠 쓰면 한쪽을 고칠 때 다른 쪽이 같이 움직인다). 캡처로 보면 두 도구는 이미
같은 디자인으로 보인다 — **분리는 코드에만 있고 화면에는 없다.** 남은 화면 목록은 만들지
않는다.

**`.card` 18개는 같은 것인가:** 아니다. 덱 카드(절대배치·회전·z)와 표면 카드는 다른 물건이다.
문제는 표면 카드끼리도 다르다는 것 — 캡처에서 모의고사 결과 ≈28px, 롤페 폼 ≈24px,

1번(테마 파생 radius)이 들어가면 이 다섯이 저절로 한 값으로 모인다 — 그게 순서다.

## 규칙 절

새 서비스를 얹을 때 지킬 것. **이 절이 이 검수의 산출물이다** — `docs/DESIGN.md` 로 옮긴다.

### 1. 클래스 명명

손님 화면은 CSS 모듈, 주최자는 `ad-*`, 편집기는 `admin.css` 의 `owner-*`. 이 셋은 섞지 않는다.
모듈에서 `.card`·`.head`·`.empty`·`.backBtn` 을 새로 정의하기 전에 `components.css` 에 있는지
먼저 본다. 공통 파일에 서비스 이름을 박지 않는다.

### 2. 공통 컴포넌트 사용

버튼·아이콘버튼·표면·칩·빈 상태는 전역 클래스를 `composes: … from global(...)` 로 끌어온다.
새 치수를 화면에서 만들지 않는다 — 만들어야 한다면 **왜 다른지를 파일 머리말에 적는다.**
헤더·관리자 진입·빈 상태·페이지네이션은 공통 부품을 쓴다. `<img>` 는 `SavableImage` 하나뿐이다.

### 3. 토큰

hex·radius·그림자 리터럴 금지. `9999px` 은 `var(--radius-full)`.
**서비스 색의 기본값은 `serviceTheme.ts` 에서 받는다** — 리터럴 hex 를 기본값으로 두면
주최자가 고른 색이 그 서비스에 영영 안 닿는다. 고정색이 필요한 자리(카메라 UI, 카드 무대,
어두운 상영관)는 그 이유를 **파일 머리말에** 적는다. 로컬 변수는 `--<svc>-*` 접두사.

### 4. 용어

화면 문구는 **손님**, 코드·타입·문서는 **방문자**. 운영 주체는 **주최자 / 최고관리자 / 스태프**
— 화면에서 "고객"은 쓰지 않는다(방문자 화면의 진입 링크만 "관리자"). 노출어는
**선물 · 뽑기 · 회**, "보상"·"추첨"·"가챠"는 코드에만. 서비스 운영 종료는 **마감**, 슬롯 대여
만료는 **종료** — 이 둘은 다른 개념이라 섞지 않는다.

### 5. 어투

**전 화면 해요체.** 확인창은 `~할까요?` 제목 + 짧은 동사형 okLabel + 감정어 없는 사실 진술 desc.
파괴적 동작도 해요체를 유지한다 — 톤을 딱딱하게 바꾸는 대신 결과를 정확히 적는다.
**막힌 기능은 왜 막혔는지 반드시 말한다** — 이유 없는 `disabled` 는 버그로 취급한다.

## 건드리지 않을 것

공통화하면서 넘지 말아야 할 선. 위 제안 중 어느 것도 여기에 닿지 않는다.

- **조작 주체 경계** — 타로는 손님이 자기 폰으로, 럭키드로우·포카(판매)는 스태프가 부스
  기기에서. `src/staff/*` 와 `photocard/StaffApp.tsx` 가 관리 셸 **밖**에 있는 이유다
  (`docs/LUCKYDRAW-REVIEW.md`).
- **슬롯 격리** — 테마·질문·권한은 slug 스코프.
- **역할 분리** — 슬롯 편집기를 주최자 `/admin` 으로 끌어오지 않는다.
- **슬롯 이미지의 `<img>` 금지** — 예외는 `SavableImage` 하나. 공통 부품을 만들면서 새
  `<img>` 를 들이지 않는다 (`npm run verify:noimg`).
- **`.admin`·`.owner` 의 고정 라이트** — 관리 도구는 어느 슬롯에서 열든 같은 색이다.
- **서비스의 정체성** — 럭키드로우의 스크래치, 타로의 카드 뒤집기, 소원나무의 등불,
  스탬프의 도장 찍히는 손맛. 억지로 묶으면 서비스가 죽는다.
